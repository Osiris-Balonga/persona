# Geographic data

## Country and territory registry

The V1 registry is a snapshot dated 2026-09-24 of the 249 assigned ISO 3166-1 alpha-2 codes. It also records the alpha-3 and numeric codes, an English name, a generation eligibility flag, and a telephone calling code when the source has one. The snapshot is regenerated with `npm run data:refresh:countries`; the two pinned source packages are development dependencies, so the API does not depend on a live external country service.

The assigned-code and English-name input is [`iso-3166` 4.4.0](https://github.com/wooorm/iso-3166), an MIT-licensed compilation. The [ISO 3166 Maintenance Agency](https://www.iso.org/iso-3166-country-codes.html) maintains the authoritative assignments; this project does not claim that the community package is an official ISO feed. The telephone input is [`libphonenumber-js` 1.13.14](https://github.com/catamphetamine/libphonenumber-js), which derives numbering metadata from [Google's libphonenumber](https://github.com/google/libphonenumber); the latter draws heavily on [ITU E.164 numbering information](https://www.itu.int/oth/T0202.aspx?parent=T0202). This is a dated mapping, not a promise that a prefix alone makes a valid or unassigned telephone number.

The snapshot has calling codes for 242 of the 249 ISO entries. `AQ`, `BV`, `GS`, `HM`, `PN`, `TF`, and `UM` have no entry in the pinned telephone metadata and carry `callingCode: null`. `PN` has a resident population but remains unavailable for beta profile generation until its local name pool is reviewed; its phone will remain `null` until a verified test range is available. Shared prefixes remain shared: for example, `US` and `PR` both have `+1`, while `CG` has `+242`.

The registry recognizes `AQ`, `BV`, `GS`, `HM`, `IO`, `TF`, and `UM` but marks resident-profile generation unavailable. These places lack a permanent resident population, so inventing a resident city or address would be misleading. Primary references include the [British Indian Ocean Territory profile](https://www.gov.uk/government/publications/british-indian-ocean-territory-knowledge-base-profile/british-indian-ocean-territory-knowledge-base-profile), the [UK overseas territories paper](https://assets.publishing.service.gov.uk/media/69b1718558d4ef5adaf0e46a/UK_Overseas_Territories_Information_paper.pdf), [Australian Antarctic information on Heard Island](https://www.antarctica.gov.au/about-antarctica/history/stations/heard-island-and-mcdonald-islands/), and the [French overseas ministry's TAAF profile](https://www.outre-mer.gouv.fr/territoires/terres-australes-et-antarctiques-francaises). An eligible code means it can enter the later data and generation pipeline; it does not assert full local name, city, address, or portrait coverage today.

Of the 242 resident-eligible codes, beta profile generation currently permits all 58 African codes, 30 European codes, plus `BT` and `MM`: 90 codes in total. Their source-backed local name pools have been reviewed for the generated examples; some remain small compatibility samples. The remaining 152 codes stay recognized in the registry and geographic audit, but profile generation is pending a local name review. Country selection without a `country` filter draws only from the available set. This review does not claim complete representation of every naming tradition within an available country.

An unknown code, an uninhabited code, or a resident code pending name review returns HTTP 400 with `UNSUPPORTED_VALUE` and `parameter: "country"`. Malformed country syntax remains `INVALID_QUERY`. The `profileGeneration` value in the coverage matrix distinguishes `available`, `pending-name-review`, and `unavailable`; the registry's `generation` flag continues to describe permanent-resident eligibility.

## City sample and coverage

The city snapshot uses [GeoNames `cities1000.zip`](https://download.geonames.org/export/dump/cities1000.zip) and [admin1 names](https://download.geonames.org/export/dump/admin1CodesASCII.txt), extracted on 2026-09-24 under [CC BY 4.0](https://www.geonames.org/about.html). Credit: **GeoNames**. Source hashes and editions are stored in `src/geography/sources.ts`. For each resident-eligible ISO code, the build keeps up to twelve most populous named populated places and adds the capital if it was outside that set. It removes duplicate city names within a code. Each city records coordinates and an administrative region when the source has one. `src/geography/city-data.ts` is a checked-in snapshot; `npm run data:refresh:cities -- <cities1000.zip> <YYYY-MM-DD> <admin1CodesASCII.txt>` rebuilds it from downloaded extracts. The source's [field definitions and inclusion criteria](https://download.geonames.org/export/dump/readme.txt) should be reviewed before updating the snapshot. A refresh must include new source hashes, provenance review, and geographic validation checks.

This is a bounded city sample, not a complete gazetteer. All 242 resident-eligible codes have at least one locality in the snapshot. Seven territories without permanent residents have none. A city filter must resolve against the selected country's sample; an unknown or mismatched city must fail rather than silently switch countries. GeoNames data is supplied as is, so the sample needs country-batch review before public beta use.

`src/geography/coverage.ts` produces one coverage row per assigned ISO code. Each category records an ingestion status, source, fallback, and review state. `pending` means the API must not claim that category is ready for the code. `automated` means schema and provenance checks ran; it does not mean human review. The checked-in source manifest in `src/geography/sources.ts` records source, usage right, edition, and GeoNames archive hashes. `validateGeographicData()` rejects missing eligible cities, duplicate identifiers, invalid codes, and ingested data without a known source and usage right. Future address, distribution, and portrait batches must add their own source and coverage entries before they can be marked ingested. Regional fallbacks must be explicit in the corresponding coverage cell.

## Names and appearance

For broader name coverage, `npm run data:candidates:names -- --countries=GH,SN,RW --output=<report.json>` collects country-specific candidate components from [Wikidata Query Service](https://query.wikidata.org/) using citizenship (`P27`), sex or gender (`P21`), given name (`P735`), and family name (`P734`). [Wikidata structured data is CC0](https://www.wikidata.org/wiki/Wikidata:Licensing). The report records each country's queries, retrieval time, and a SHA-256 digest of its aggregate source rows. It contains only name-component counts, never person records. Each completed or failed country is saved immediately; rerunning the same command skips completed countries and retries failures. The command exits unsuccessfully while any country has failed. The [public query service](https://www.mediawiki.org/wiki/Wikidata_query_service/User_Manual) limits queries to 60 seconds and may throttle clients, so failures must stay visible rather than be silently treated as empty countries.

The collector stops after two consecutive country failures, leaving unattempted codes pending for the next run. The report is research input and is kept outside the runtime catalog. Counts measure Wikidata coverage, especially public-figure coverage, not population frequency. An editor must inspect local plausibility, spelling, gender ambiguity, and second-name usage before moving a country into the checked-in catalog. Sparse results stay sparse; names from another country are not added to meet a target count. The current small reviewed pools are compatibility samples and need this broader review before the public beta.

If WDQS is unavailable, rerun the same command with `--engine=qlever`. [Wikidata lists QLever as an alternative endpoint](https://www.wikidata.org/wiki/Wikidata:SPARQL_query_service/Alternative_endpoints); its [usage information](https://github.com/ad-freiburg/qlever/wiki/Usage-and-privacy-information-for-the-QLever-SPARQL-endpoints) applies. QLever queries use English Wikidata labels explicitly, so an entity without an English label will be absent from that candidate report. The per-country `source` and query fields identify which endpoint produced each result, including when a resumed report combines endpoints. Do not compare the counts from the two engines as if they were population statistics.

For codes where citizenship does not identify the territory, `npm run data:candidates:names -- --countries=DJ,EH,ER,GW,KM,LY,MR,NE,SH,ST,SZ,TD,YT --engine=qlever --basis=birthplace --output=data/geography/africa-birthplace-candidates-2026-09-24.json` collects a separate aggregate report using Wikidata birth place `P19` and administrative hierarchy `P131*`. The pinned snapshot SHA-256 is `a42dceddd27373a2ce32353ccb26582992e6b5718f91aa48a8b3b826fd26fc58`. All 13 queries completed; only `LY` reached 50 raw entries in every field. Birth place is not evidence of current residence, citizenship, or local name frequency, so these candidates require independent review before use.

Run `npm run data:audit:names` for per-code candidate counts, rejected labels, gender ambiguity, first/second-name overlap, format warnings, endpoint, and source hash. The snapshot is a review queue, not a runtime pool or a country-readiness decision. The name snapshot combines [GeoNames `countryInfo.txt` language tags](https://download.geonames.org/export/dump/countryInfo.txt) (CC BY 4.0; credit: **GeoNames**) with the [MIT-licensed person locale data in `@faker-js/faker` 10.6.0](https://github.com/faker-js/faker). It is regenerated with `npm run data:refresh:names -- <countryInfo.txt>` after the source hash is reviewed and updated. The runtime uses the committed snapshot, not the source packages or a remote service. Each eligible code has one or more named pools. An exact country locale is labelled `local`; a shared language locale is `language`; `en` is the explicit global fallback when no listed language has a supported name pool. When country-specific pools exist, selection uses only those pools; otherwise it uses the supported language pools. The first listed language has editorial weight 4, the second 2, and later supported languages 1 each. These weights are a reproducible selection rule, **not demographic estimates**. All pool weights and nonlocal fallbacks appear in the source data and coverage matrix. A sampled name may still be culturally inappropriate; country-batch review remains necessary before beta release.

The V1 appearance vocabulary is `west-african`, `central-african`, `east-african`, `southern-african`, `north-african`, `middle-eastern`, `european`, `south-asian`, `east-asian`, `southeast-asian`, `latin-american`, and `mixed`. These are broad visual catalog labels, not nationality, ethnicity, or a reliable inference about a person. Name pool selection takes the country and gender but never the appearance or portrait. A requested country and appearance can be combined independently. The portrait catalog will separately validate compatible images; no image is generated by a request.

## Fictional addresses

Country address order and required fields come from [Google's Address Data Service metadata](https://github.com/google/libaddressinput/wiki/AddressValidationMetadata), licensed [CC BY 4.0](https://github.com/google/libaddressinput) for the data. Credit: **Google**. The 2026-09-24 snapshot contains all 249 assigned codes; 195 have an explicit country format, and 54 use the documented generic format. Run `npm run data:fetch:address-metadata -- <output.json>` to fetch a new source copy, then review its hash and license before running `npm run data:refresh:addresses -- <output.json> <postal-allCountries.zip>`. API requests use the checked-in snapshot only.

City-linked postal examples come from [GeoNames' postal extract](https://download.geonames.org/export/zip/) (CC BY 4.0; credit: **GeoNames**). The build keeps a full-format postal code only when its place name matches a sampled city and its coordinates are within 25 km of that city. This currently yields 553 sampled cities across 78 country codes. It never borrows a code from a different city or fabricates one from a country-wide pattern. GeoNames notes that its postal extract covers roughly 100 countries and includes partial codes in some places; partial codes are rejected by the country format check. Coverage is consequently marked `partial` where a required code or region is missing, a generic format is used, or the street style falls back to English.

The street line uses clearly illustrative words such as “Example” or “Exemple”, with a stable building number. Its language follows the country-language snapshot independently of any curated name pool. The structured address includes `line1`, `city`, nullable `region`, nullable `postalCode`, `country`, and `formatted` in the country's published field order. It is intended for mockups and tests, not delivery or geocoding. A nullable postal code signals missing city-linked evidence, including in countries where a deliverable address would normally require one. The data snapshot and coverage matrix make that limitation visible rather than returning a mismatched value.

Pitcairn is an explicit exception: the [Universal Postal Union](https://www.upu.int/UPU/media/upu/PostalEntitiesFiles/addressingUnit/pcnEn.pdf) documents `PCRN 1ZZ` as the single postcode for the territory. Its illustrative line omits a building number. The exception is recorded separately from the GeoNames postal extract so it is not presented as a city match found there.

## Catalog validation and audit

The refresh scripts check pinned source hashes before generating snapshots. ISO records are unique by code. The city build keeps one entry per case-folded name and country, retaining the more populous candidate in its bounded sample. Name arrays remove exact duplicate strings before even sampling. Postal examples are keyed by GeoNames city ID and retain the nearest full-format match within 25 km. Every ingested coverage cell has a licensed source in the manifest; additional inputs such as language tags, administrative names, postal codes, and the UPU Pitcairn exception are listed separately.

Run `npm run data:audit` for a concise status or `npm run data:audit -- --json` for every per-code gap. The audit checks all 249 registry codes, generates controlled male and female geographic/contact samples for all 242 resident-eligible codes, validates city/country relationships and address output, and fails on malformed samples or missing source rights. It lists partial data and review work without marking machine-checked names or addresses as culturally reviewed. The HTTP and portrait audit is tracked in the public-beta Epic after those components exist.

The audit and the later response metadata use `geographicDataVersion`, separately from the ISO registry edition used as the audit's fixed `asOf` date. Bump the geographic data version whenever a snapshot or its generation policy changes, so a seeded response cannot silently reuse a version label for different data.

## Fictional telephone policy

Telephone output is optional. A calling code is metadata for validation and presentation; it is never sufficient to invent a safe subscriber number. A country receives generated telephone numbers only after a country-specific, officially reserved fictional/test range has been reviewed and versioned. Otherwise `phone` is `null`. The API must not suggest that a format-valid random number is unassigned, reachable, or safe to call.

[NANPA's reserved 555-0100 through 555-0199 block](https://nanpa.com/numbering/555-line-numbers) and [Ofcom's UK drama ranges](https://www.ofcom.org.uk/phones-and-broadband/phone-numbers/numbers-for-drama) provide the first reviewed ranges. Each batch must tie a reserved range to the correct national or area prefix and test an E.164-formatted output. No arbitrary subscriber numbers will be emitted for other countries.

The first phone batch uses NANPA's `202-555-0100` through `202-555-0199` only for a generated Washington, US resident, and Ofcom's UK-wide mobile drama range `07700 900000` through `07700 900999` for GB. Values are emitted in E.164 form and selected from a stable generation key. The coverage matrix marks the US as partial because its other sampled cities have `phone: null`. Other country codes currently return `phone: null`. New ranges require official allocation evidence and city or nationwide applicability before use.

Email values are generated under the reserved `example.test` domain. Accented Latin names are folded for the local part; a stable key suffix prevents common-name collisions within a response. For scripts that do not fold to ASCII, the local part falls back to `person`. The contact fields are illustrative and must never be used to deliver mail or place calls.
